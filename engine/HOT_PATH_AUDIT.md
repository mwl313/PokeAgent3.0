# Native hot-path audit — 2026-10-07

The full Champions M-C engine goal remains active. All 1,136 M-B/M-C teams remain training teams. No coverage restriction, team filtering, altered probability, rounding approximation or reference execution was introduced. Current runtime support remains incomplete; this audit evaluates the actual implemented paths, not readiness of unimplemented mechanics.

## Actual issues found

1. `queue.rs::speed_sort`: a temporary tie-index `Vec` was allocated on every sort, including tiny and empty recipient lists. Now uses inline `SmallVec<[usize;32]>`; selection, swaps and forward shuffling are identical. Larger lists spill onto the heap without dropping handlers. A new 70-tied-handler oracle fixture tests that spill path.
2. `battle.rs::{each_update,targets,use_move,residual}` and `battle/weather.rs::field_change_order`: temporary active entities, speed pairs, hit lists, damage lists and residual handlers repeatedly allocated. They now use inline small vectors, preserving iteration and recipient order. Type effectiveness folds the at-most-two defender types directly, preserving immunity and stage clamping.
3. `battle/hooks.rs::{modifiers,damaging_hit,ability_start}`: modifier and target-handler vectors allocated even with zero recipients, several times per damaging target. Inline storage now avoids common-case heap use. Conditional no-op hooks remain present because removing them can alter tie RNG.
4. `actions.rs::Request`: candidate feasibility allocated preview/bench/move/scratch lists; `validate_joint` additionally regenerated feasible alternatives for each chosen prefix. Inline lists, `candidates_into` and direct full-sequence validation remove this churn. Each chosen action must still belong to its native raw prefix candidates; a complete valid sequence is itself its completion witness. Candidate capacity checks remain explicit errors, never truncation.
5. `batch.rs::BattleBatch::step_batch`: each call allocated environment routing and intermediate results, sorted them, then allocated output again. `step_batch_into` retains routing/results across calls and writes to caller-owned output in submitted handle order. Whole-batch preflight remains before state mutation. A focused test covers reversed/sparse handles, repeated caller-buffer use, rejected duplicate submissions, unchanged snapshots and an empty batch.

## Architecture after changes

The engine retains the complete pinned catalogue as shared immutable indexed metadata, including a conservative dependency superset. Submitted sets are validated directly rather than pre-enumerated. Each battle stores its twelve roster members, four active positions, runtime effect states, numeric IDs, RNG and player knowledge. Events gather only local recipients and dispatch static handlers; inline lists spill safely if needed. Actions derive from native requests, and observations contain battle-local categorical data. Batch work/results reuse buffers. This is the structure for completing full M-C semantics; the still-unsupported handlers and dynamic closure must be implemented before training readiness.

## Benchmark

Engine-only replay, release Rust 1.90.0, Xeon E5-2673 v4, two sockets with 20 physical cores each/80 logical CPUs. No affinity or NUMA placement applied. The same 95 complete legal synthetic fixture battles were repeated across 2,048 environments, producing 59,307 player-side submissions, mean 28.96 per battle. Counting the fixture request boundaries gives 32,330 committed decision advances, mean 15.79 per battle (including preview, replacements and terminal advances; excluding reset and pending first-side submissions). Submissions include one-side pending decisions; they are not committed full-turn transitions. Cold Dex/reset/JSON/fixture construction is outside timing. Natural outcomes are asserted; there is no policy, model inference or Python bridge.

Medians of three uninstrumented runs, before versus after allocation changes:

| Configuration | Native side submissions/s before → after | Naturally completed battles/s before → after |
|---|---:|---:|
| 1 worker, steps only | 87,060 → 242,332 | 3,006 → 8,368 |
| 2 × 16 workers, steps only | 277,989 → 1,011,853 | 9,600 → 34,942 |
| 1 worker, views + first-prefix candidates + steps | 38,124 → 65,576 | 1,317 → 2,265 |
| 2 × 16 workers, views + first-prefix candidates + steps | 117,977 → 119,177 | 4,074 → 4,115 |

Parallel timings vary; the observation-inclusive 32-worker result shows little throughput improvement and does not justify a broad speedup claim. At one worker, median observation time for this workload was 335.695 → 266.554 ms and first-prefix candidate time was 192.809 → 135.979 ms. Owned view destruction and orchestration also consume time outside those two component timers. These are first-prefix generation costs, not all policy branch selections.

A separate instrumented pass counted allocations/reallocations, not live memory: one-worker step-only calls fell from 7,072,799 to 369,401 (94.8% fewer); requested bytes fell from 236,755,200 to 20,346,326. With views/candidates, calls fell from 10,957,529 to 2,741,972 and requested bytes from 836,982,232 to 574,884,498. Atomics distort instrumented timings, especially across threads; use uninstrumented medians for speed comparisons. Counter-disabled output zeros mean not measured, not allocation-free.

After-change process RSS at the prepared 2,048-env points was about 52.8 MiB for the one-worker steps-only case and 82.6–83.0 MiB for two groups. Observation-inclusive cases ranged roughly 103–123.8 MiB in the three timing runs. RSS includes shared Dex, fixture teams, prebuilt action rounds, thread stacks and retained allocator memory; it is not exclusive per-environment RAM or a NUMA-local memory measurement.

Separate single-run component probes: direct untraced `BattleState::step` replay measured 330,361 side submissions/s and 11,408 natural games/s; explicit trace measured 269,308 submissions/s and 9,300 games/s (initial snapshot creation outside timing). Idle 2,048-state batch scan measured 31.123 µs/call with one worker and 125.668 µs with 16 workers; it includes buffer clearing and Rayon dispatch but no active validation/mechanics, so it is not active scheduling overhead. The `speed_sort` primitive measured 186.6 ns for four distinct-speed handlers and 88.9 ns for four tied handlers, including input copying. Full event/effect processing and active scheduling are included in step totals and not isolated; bridge/model performance is unmeasured because those paths do not exist.

Raw measurements: `benchmarks/hot_path_before.txt`, `hot_path_after.txt`, `hot_path_components.txt`, host/method metadata `hot_path_metadata.json` and request-count metadata `hot_path_workload.json`. Reproduce current probes with `bash scripts/cargo.sh run --release --locked --example hot_path_bench`, add `-- --count-allocations` for counts, and run `--example hot_path_components` for components. Subsequent mechanic/fixture additions change the workload; the saved comparison refers to the 95-fixture audit stage.

### Subsequent suppression probe

After Cloud Nine/Air Lock and snapshot schema 3 were added, `hot_path_suppression.txt` records three runs over the identical historical 95 inputs: medians 7,006 and 31,484 step-only games/s (one and 32 workers), with exactly the same 369,401 one-worker allocation calls. A no-weather early return then removed unnecessary suppressor scans when stored weather is absent. Its three-run results in `hot_path_suppression_fast_none.txt` measured medians 5,976 and 29,040 step-only games/s, and 1,997 / 3,120 games/s with owned observations/actions. Timing variation across these sequential probes also affected unchanged observation/action code; it does not prove a speed benefit from the early return or isolate suppression CPU cost. The structural improvement avoids unnecessary local work; no heap churn was introduced. The 115-fixture default single probe is saved separately in that same file; its changed workload must not be compared directly with the original 95-fixture throughput table. Current RSS also includes cold parsing of all 115 fixtures before the historical subset is selected.

`hot_path_bench --audit-baseline` selects only the original 95 inputs for comparison. Its 95 names are pinned in `hot_path_baseline_names.json`; canonical seed/team/action input hashes in `hot_path_baseline_inputs.json` were checked unchanged after the 172-case export. This is a development benchmark flag; the default benchmark and differential/parallel tests retain all 172 cases, and the regulation/training pool is unchanged.


The expanded 136-fixture single native-only probe is saved in `benchmarks/hot_path_weather_abilities.txt`: step-only throughput was 7,737 completed fixture battles/s with one worker and 29,628 with two groups of 16 workers (231,205 / 885,349 side submissions/s; 29.88 submissions/battle). With owned observations and first-prefix candidates, throughput was 1,556 / 3,705 battles/s. One-worker measured observation and candidate totals were 355.502 ms and 199.674 ms for the 2,048 games. Process RSS was approximately 65.5 / 95.1 MiB step-only and 121.5 / 149.8 MiB with observations. These are single probes over recorded legal fixture actions, not policy/model throughput, and the changed workload is not a before/after comparison. Allocation counters were disabled (printed zeros do not mean zero allocations); bridge time and NUMA placement remain unmeasured.

The encoder probe in `benchmarks/observation_encoder.txt` measures preview observations for all 1,136 teams, with 2,048 distinct reusable outputs, 64 iterations and three repetitions per mode. Median serial encoding of cached safe views was 69,833 views/s (29.327 ms per 2,048 views); total native view construction plus encoding measured 63,853 views/s with one worker (32.074 ms), and 171,222 views/s with two concurrent 1,024-env/16-worker groups (11.961 ms). Cold Dex/Encoder validation, resets and warm-up are excluded; the cached-view mode excludes view cloning/scheduling, while total modes include them. These are preview-only encoder measurements, not full-battle observations, natural games, Python bridge, model inference or NUMA performance. No allocation counter or exclusive environment-memory claim is made for this probe.

## Remaining risks

- Owned observations, requests, pending action vectors, effect maps and compatibility APIs still allocate. Numeric output buffers now reuse storage even after sparse/empty requests, but player-view construction still clones owned requests/knowledge; Python tensor export and further measured allocation work remain required.
- Native legality is structural/catalogue based and does not yet cover all cross-rule legality. Full event handling, rare interactions, Mega transitions and dynamic closure remain incomplete.
- Worker count is not physical-core placement. NUMA-local actor integration and PyO3 methods remain required.
- Reference sorting is exact but quadratic; current recipient lists are small. Broader active effect lists need profiling without changing tie semantics.
- Allocation counters and subset replay benchmarks are useful engineering evidence, not full-regulation training throughput or competitive model evidence.
